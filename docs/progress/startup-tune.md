# Startup tuning (sensorless low-speed start): progress

Branch `ccr-5bff181d-bhhb1d`. A tool VESC Tool doesn't have: it runs sensorless FOC starts on the controller, measures each one with everything the firmware exposes, and searches the observer and open-loop settings that start the motor best.

Sources: `vedderb/bldc` master = 7.01 (`motor/mcpwm_foc.c` open-loop sequence and current controller, `motor/foc_math.c`, `motor/mc_interface.c` sampling, `comm/commands.c`, `lispBM/lispif_vesc_extensions.c` conf-set/conf-get/measurement extensions, `lispBM/README.md`, `lispBM/lispBM/doc/lbmref.md`) and the `release_6_05`, `release_6_06`, `release_7_00` branches for what older firmware has, read 2026-11-04.

## How it works

1. **Probe.** `core/vesc/src/main/resources/app/foctuner/vesc/tune/startup_probe.lisp`, streamed (`COMM_LISP_STREAM_CODE`, reset and load, never stored) after `LispCode.reduce`. It answers commands sent as `COMM_CUSTOM_APP_DATA` (`event-data-rx`) and replies with `send-data`. Commands: hello (selects motor 1 or 2), set and get parameters with `conf-set` / `conf-get` (RAM only), measure resistance (`conf-measure-res`), run a start, stop, quit. A start waits until the rotor has been still (≤ 4 s), disables app output for its length, drives `set-current` and samples every 4 ms: `get-rpm`, `get-rpm-faster`, `get-iq`, `get-id`, `get-iq-set`, `get-vd`, `get-vq`, `phase-observer`, `phase-motor`, `get-duty`, `get-est-lambda`, `get-est-res`, 26 bytes a sample, 8 samples a packet. It stops at the target speed, the time limit, a fault, a temperature or voltage limit, or a stop command, reports the end (outcome, reach time, fault, voltage, temperatures, estimates), brakes with half the start current below 150 ERPM and reports the release. Errors inside a start are trapped and release the motor. Protocol 2 adds a dead man's switch: at the first hello the probe saves every parameter it can read (`ft-orig`, 5 bytes each); a watchdog thread (`ft-watch`, every 250 ms) sets them back with conf-set, re-enables app output, reports 138 and stops answering once no command has arrived for `ft-quiet` (5 s) while no start or measurement runs. The app pings (command 8) every second while it holds the probe (`StartupProbe.keepAlive`), so a lost link or a killed app can't leave test values in use until the next reboot. Quit doesn't restore, so Use until reboot keeps its values.
2. **Side channels** (`StartupTuner`), alongside every start: realtime values (`COMM_GET_VALUES_SELECTIVE`, 5 Hz: temperatures, input voltage and current, fault, status) to stop at limits and report peak battery current; the observer angle stream (`COMM_SET_DETECT` observer mode, `COMM_ROTOR_POSITION`, 100 Hz); phase currents at switching rate for the first start of every candidate (`COMM_SAMPLE_PRINT`, start trigger, 500 samples spread over the open-loop sequence and the handover); the firmware's resistance measurement before the search; the `faults` terminal output after a fault.
3. **Analysis** (`StartupAnalysis`), per start:
   - open-loop sequences: the firmware overrides the FOC angle while its open-loop sequence runs (`m_phase_observer_override` in `mcpwm_foc.c`), so `phase-motor` differs from `phase-observer` (by about 45°: the observer is seeded 45° ahead). Count, duration, speed lost after the last handover, and the acceleration right after it relative to later (the torque the observer's angle still produced).
   - observer angle error: the back-EMF in the controller frame from the firmware's own dq model, e = v − R·i − jω·L·i (vd = R·id − ω·Lq·iq, vq = R·iq + ω·Ld·id + ω·λ, Lq/Ld = L ± ΔL/2), where it is readable (ω·λ ≥ 0.5 V and ≥ 2·R·|iq|): angle atan2(ed, eq), RMS and peak. During open loop the same back-EMF gives the rotor's speed against the open-loop speed (does the rotor follow the ramp).
   - flux linkage seen while running (|e| / ω and the observer's own estimate), backward travel, ripple of the fast speed estimate, q current tracking, duty peak; from the phase currents the peak over the start current, the spread of the current vector length and FOC angle jumps; from the rotor stream backward steps of the observer angle while the motor is slow (below 1500 ERPM, where 100 Hz can still tell direction).
4. **Cost** (`StartupCost`): time to the target over the starting settings' median, plus terms scaled so 1 means "noticeably bad": extra open-loop sequences, speed lost and torque lost at the handover, backward speed, ripple, angle error, open-loop slip, current peaks, observer reversals. A start that didn't reach the target costs 10 to 20 by how far it got, a fault 30.
5. **Search** (`StartupTuner`): starting settings, then one parameter at a time from the best so far: the measured resistance taken to the reference temperature (if it differs by more than 8 %, 18 % without a motor temperature sensor, and the hardware has phase filters), the flux linkage the starts showed (if two sources agree), observer type (thorough, firmware 6.06+), observer gain ×0.5/0.7/1.4/2, open-loop ERPM ×0.6/0.8/1.25/1.6 (at most half the target), and with thorough lock, ramp and open-loop time. Three starts per candidate, alternating direction unless the run is forward only; with the current sweep the three starts run at 0.5, 1 and 1.5 times the start current (capped at `l_current_max`) and each start's time is judged against the starting settings at its own current. A candidate replaces the best when it costs 3 % less (mean, so a failed start counts in full). Then at least 3 (thorough 4) interleaved pairs of starting and best settings, same current and direction within a pair; the result is recommended only if its median cost is at least 10 % lower, it wins most pairs and has no more timed-out or faulted starts. A result at least 3 % better but not accepted gets up to 3 more pairs: the best is the lowest of many noisy scores and tends to look better in the search than it is. The starting values are set back in every case (`finally`, by the probe, by the probe's own switch, or by writing the config as read, which also stores it; `TuneReport.restore` and `TuneAbortedException.restore` say which, and the tool says so), LispBM's stored code is started again if it was running, otherwise LispBM is paused.
6. **Tool** (Detection › Startup tuning): current settings, test settings (current, target, time limit, thorough, several currents, both directions, phase current recording, off by default over BLE), estimate of starts and minutes, confirmation, progress with the last start's speed (open-loop band) and current, findings, every candidate's score, Save every start as CSV (`StartupCsv`), Apply (stores the changes), Use until reboot (`conf-set` through a short-lived probe), Discard.

Resistance and temperature: copper rises about 0.39 % per °C, so 20 °C of heating moves R by about the 8 % threshold. The measurement is taken back to the reference temperature (`foc_temp_comp_base_temp` when the firmware's temperature compensation is on, else 25 °C, where detection usually runs) with the motor temperature read just before it; the analysis model follows each start's motor temperature from there. Without a motor sensor the thresholds are 10 % wider and the finding says the temperature is unknown.

Defaults: start current a quarter of `l_current_max` (2..40 A); target twice the highest open-loop ERPM tried, at least 1500 and at most 40 % of the no-load speed at the pack voltage; 3 s per start, shortened to 2.5× the starting settings' slowest start once they all succeed. Limits: 5 °C below `l_temp_fet_start` / `l_temp_motor_start` (motor ignored without a sensor), 0.5 V above `l_battery_cut_start`. Refuses firmware before 6.05, non-FOC, sensor modes other than sensorless, undetected motors (R, L or λ zero), an active fault, an active kill switch, a turning motor, low voltage, heat.

## Testing fixes (2026-11-05)

From running the tool on an emulator in demo mode (dark theme: full run, stop mid-run, a detuned motor, Use until reboot, Apply).

- A stop that reached the probe between starts was lost: the next `ft-start-trial` clears `ft-stop`, and the monitor sent stop once. With the kill switch on, one more full start ran. `countedTrial` now checks the abort before every start and the monitor stops on every poll once aborted. `StartupTunerTest.aKillSwitchBetweenStartsKeepsTheNextStartFromRunning` failed without the check. The repeated stop closes the instant between that check and the trial command, which a test can't reach.
- An active kill switch is refused before the run (`TuneRefusal.KILL_SWITCH`); `SimulatedVesc.killSwitch` sets it in the status byte.
- Stop said nothing about the starting values: a cancelled or failed run has no report and no `TuneAbortedException`. `StartupTuner.restoreResult` holds how they got back and the tool shows it. It stays null when the run changed nothing.
- `SetupRunner.busy` went false as soon as Stop was pressed, while the tuner was still restoring, so a new run could read test values as its starting values. It now lasts until the job has ended.
- "Current start settings" went stale: the model outlives the screen and read the config once. It reads again each time the tool opens, and after Apply and Use until reboot.

## Unverified

- Nothing has run on hardware. The probe script has never been evaluated by LispBM: the lint checks syntax, names, arity and layout, not semantics (number conversions in `bufset-*`, `spawn` with a stack size, `trap` results, events while a start runs).
- The dead man's switch has never run on LispBM either: a watchdog thread with a 256-word stack, conf-get into a buffer at hello, conf-set from that thread. Check on the bench that it restores after the app is killed mid-run and that pings keep it quiet over BLE.
- LispBM heap: the protocol 2 additions are roughly 150 more cons cells. The probe's code is about 1.6k cons cells (≈1.8k with bindings) of 2464 on 6.05 and about 2.7k on 7.01. The drive loop allocates boxed floats, so garbage collection will run often; the 4 ms period may stretch.
- `conf-set` of `foc-motor-r` / `foc-motor-flux-linkage` / the observer and open-loop parameters calls `mc_interface_set_configuration` while the motor is idle; assumed free of side effects.
- The angle error estimate assumes `get-vd` / `get-vq` are the applied voltages (they are the controller's output, so dead time and the voltage limit add error) and the firmware's sign conventions as read from `mcpwm_foc.c`. The cost uses its RMS, so a sign error wouldn't matter; a model error would show as a constant offset on every candidate.
- `COMM_MOTOR_ESTOP` should stop a start the probe drives (it makes `mc_interface` ignore input); not tested.
- Dual boards: motor 2 is picked when the selected CAN controller reports the attached board's UUID with the last byte + 1, and the rotor stream is skipped for it. Not tested.
- The simulator's start model is phenomenological: it reproduces the mechanisms (open-loop speed below the observer's lock speed, slip on a steep ramp, λ and R bias), not a particular motor's numbers. The end-to-end test proves the search and the plumbing, not the weights.
